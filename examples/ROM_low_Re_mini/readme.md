# ROM_low_Re_mini

Each ROM mini example has exactly one case file. All four examples use the
same real Neko-TOP fluid/scalar physics, design mapping, objectives and
ROM-MMA lifecycle; they differ only in the selected forward/adjoint basis
pair.

| Example | Forward basis | Adjoint basis |
| --- | --- | --- |
| `ROM_low_Re_mini` | `forward` | `forward` |
| `ROM_low_Re_mini_separate_pod` | `forward` | `adjoint` |
| `ROM_low_Re_mini_forward_enriched_adjoint` | `forward` | `enriched` |
| `ROM_low_Re_mini_enriched_galerkin` | `enriched` | `enriched` |

Run it through the normal repository launcher:

```bash
./run.sh ROM_low_Re_mini -c
```

Replace `ROM_low_Re_mini` with one of the other example directory names to run
that basis pair. Each directory contains a matching case file, `run.sh`,
`prepare.sh` and ROM user component. The mesh is generated by `prepare.sh`
with Neko's `genmeshbox` tool.

The public ROM interface is deliberately small. Put ROM settings under
`optimization.solver.rom`; select the two basis names and set the history
length. The number of modes per streamed POD block is controlled only by
`state_recovery.n_modes`; all independent modes received from the available
history are retained after projection and linear-dependence rejection.

The canonical interface is:

```json
"optimization": {"solver": {"rom": {
  "basis": {"forward": "forward", "adjoint": "adjoint"},
  "inner_iterations": 5, "history_outer_iterations": 3,
  "substeps": 4
}}}
```

The supported basis pairs are `(forward,forward)`, `(forward,adjoint)`,
`(forward,enriched)` and `(enriched,enriched)`; each is represented by its own
example directory and case file.
Formulation names, `sensitivity_source` and rank fields are obsolete in
migrated cases. The old top-level `rom` object remains a narrowly scoped
compatibility path for older examples; this case uses the nested object above.

ROM output is permanently indexed by the physical design entering each ROM
lifecycle. The first reference lifecycle is `outer_000`. Its standard Neko
field-output streams start at `f00000`; later inner candidates are `f00001`,
`f00002`, and so on. The field counters restart for each outer directory:

```text
rom_output/
  outer_000/
    forward_pod_coefficients.csv
    adjoint_pod_coefficients.csv
    basis_metadata.json
    forward_fields0.f00000
    forward_fields0.f00001
    design0.f00000
    design0.f00001
    sensitivity0.f00000
    sensitivity0.f00001
    forward_coefficients_inner_000.csv
    adjoint_coefficients_inner_000.csv
    objective_diagnostics_inner_000.csv
    forward_coefficients_inner_001.csv
    adjoint_coefficients_inner_001.csv
    objective_diagnostics_inner_001.csv
  outer_001/
    ...
```

POD modes, singular values, recycled-history metadata, trajectory fields,
design/sensitivity fields and reduced-system exports remain below their
matching `outer_NNN` directory. Each `objective_diagnostics_inner_NNN.csv`
records the outer/inner indices, objective components, constraint, timings,
sensitivity source and the associated design/coefficient filenames. The root
`optimization_data.csv` remains the ordered mixed history: full-order
`outer` row, ROM `inner=0` reference row, then ROM inner updates.

For compatibility, root-level files such as `pod_time_coeffs.csv`,
`adjoint_pod_time_coeffs.csv`, `recycled_rom_history.json` and
`basis_metadata.json` are explicit symlinks to the newest permanent copy;
they are not the archival storage. The Fortran reduced-system export is
stored at `rom_output/outer_NNN/reduced_system/metadata.json`.

The objective weights in all four comparison cases are `(120, 15, 15)` for
scalar mixing, viscous dissipation and Brinkman dissipation. The existing
admissibility and objective/gradient validation gates remain active; a run is
an engineering experiment unless those records pass.
